# v2.0.0 — Google Auth + Cloud Deck Sync

> **Status: IMPLEMENTED (v2.0.0).** Drafted by Claude Code, decisions confirmed
> by Phi (resequence ✓, v2.0.0 ✓, DECISIONS.md log ✓), then built. The body
> below is the contract as designed; **As-built deltas** at the very bottom
> records where the implementation simplified the plan. Requires the one-time
> external setup in the **Setup / config** section before it activates.

## Overview

Add optional Google sign-in and cloud sync so a signed-in user's decks follow
them across devices, and so a small group of invited testers can each have their
own private deck library. The app stays fully usable **signed out** — local-only,
exactly as today. Signing in is purely additive: it turns on sync and merges
existing local decks up to the cloud.

Backend is **Supabase** (the choice already named in `PRODUCT.md` Phase 4 and
`SCHEMA.md`): Postgres + Row-Level Security for per-user isolation, and Supabase
Auth with the Google provider so we don't hand-roll OAuth.

### Resequencing flag (for Phi)

`docs/PRODUCT.md` places accounts + Supabase sync at **Phase 4** — last, *after*
the surface rebuild, IA/mobile, and brew mode — with the explicit rationale that
"doing it before the surface is right would mean redesigning it twice." This spec
pulls that forward to meet two concrete present needs: cross-device building for
Thurgood, and private libraries for a few invited testers. That is a deliberate
resequencing of a documented decision, not an oversight. The design below
mitigates the "redesign it twice" risk by (a) storing each deck's cards as an
opaque JSONB blob that mirrors today's `Deck` shape, so the data layer does not
encode assumptions about the surface, and (b) keeping all sync behind the
existing `DeckProvider` chokepoint so surface churn doesn't ripple into it.
**If Phi would rather hold to the documented phasing, stop here.**

## Product guardrails (non-negotiable, from PRODUCT.md)

- **No account required to try.** Signed-out is the default and loses nothing.
  localStorage remains the signed-out store.
- **Optional, generous.** No paywall, no gate, no nag. Sign-in is one button in
  Settings. The home/empty-state copy must not imply an account is needed.
- **Private by default.** A signed-in user sees only their own decks. No sharing,
  no public decks, no social surface in this version — RLS enforces isolation.

## Implementation phases

Ship in order; each phase leaves the app deployable.

### Phase 1 — Auth foundation (no sync yet)
Wire Supabase Auth + Google provider, an `AuthProvider`, and sign-in/out UI.
Signed-in state exists but does nothing to deck storage yet. App behaves exactly
as today regardless of auth state. This phase is independently shippable and
verifiable (you can sign in and see your email; decks still come from
localStorage).

### Phase 2 — Schema + cloud read/write for signed-in users
Create the `decks` table + RLS. Add the `SupabaseStore` adapter. When signed in,
`DeckProvider` reads/writes the cloud instead of localStorage. **No merge logic
yet** — a brand-new signed-in user starts with an empty cloud library. (Tested
with a throwaway account so we don't need merge to validate the round-trip.)

### Phase 3 — First-login merge + multi-device sync
On first sign-in, merge existing local decks up to the cloud. On subsequent
loads, pull cloud → local. On change, debounced push local → cloud. Last-write-
wins per deck via `updated_at`, with a gentle "loaded newer version from another
device" toast when a remote-newer deck is detected on load.

### Phase 4 — Tester onboarding polish
Whatever the first real multi-user test surfaces: clearer signed-in indicator,
sign-out confirmation, an account/sync section in Settings showing last-synced
time. Scope finalized after Phase 3 is in real use.

## Tech decisions

### Supabase, not a hand-rolled backend
Native Google OAuth provider, Postgres, RLS for isolation, generous free tier
(far more than "Thurgood + a few friends" needs), first-party JS SDK
(`@supabase/supabase-js`) plus `@supabase/ssr` for Next.js App Router session
handling. The anon/public key ships client-side and is **safe** precisely because
RLS — not key secrecy — enforces access. This is the documented Phase 4 choice.

### Google OAuth only (this version)
One provider keeps the surface minimal and matches the request. Email/password,
magic links, and other providers are out of scope. Supabase makes adding more
providers later a config change, not a rewrite.

### Local-first with optional cloud sync (not cloud-first)
The app is 100% localStorage today and the product promises "no account required
to try." So the model is: **signed out = local (unchanged); signed in = cloud,
seeded once from local.** We do not rip out localStorage or require login. This
preserves the product promise and de-risks the migration — the local path keeps
working throughout.

## Data model

### `decks` table

```sql
create table public.decks (
  id            uuid primary key,             -- keep the client-generated id (crypto.randomUUID)
  user_id       uuid not null references auth.users (id) on delete cascade,
  name          text not null,
  format        text not null default 'freeform',  -- 'freeform' | 'standard' | 'commander'
  commander_ids jsonb not null default '[]'::jsonb, -- string[] of card ids (0–2)
  cards         jsonb not null default '[]'::jsonb, -- DeckCard[] — main deck
  sideboard     jsonb not null default '[]'::jsonb, -- DeckCard[] — sideboard
  updated_at    timestamptz not null default now(),
  created_at    timestamptz not null default now()
);

create index decks_user_id_idx on public.decks (user_id);
```

**Why cards/sideboard as JSONB blobs, not a normalized `deck_cards` table:** the
whole deck loads and saves as a unit, there is no cross-card querying, and the
blob mirrors today's `Deck` / `DeckCard` shape (`src/types/index.ts`) almost 1:1
— minimal refactor inside `DeckProvider`. A `DeckCard` is a full `ScryfallCard`
plus `quantity`, `ownedQty`, `isOwned`; we store the same object we already keep
in localStorage. **Revisit only if** collection-wide owned-tracking across decks
becomes a feature (e.g. "how many of this card do I own across all decks") — that
would justify normalizing card rows. Flag noted; do not normalize pre-emptively.

> Storing the full Scryfall card object per deck-card duplicates a lot of card
> data, exactly as localStorage does today. That's intentional for parity and
> simplicity. If row size becomes a concern at scale (it won't for this user
> base), a later migration can store card ids + a shared printings cache. Out of
> scope here.

### Row-Level Security

```sql
alter table public.decks enable row level security;

create policy "own decks: select" on public.decks
  for select using (auth.uid() = user_id);
create policy "own decks: insert" on public.decks
  for insert with check (auth.uid() = user_id);
create policy "own decks: update" on public.decks
  for update using (auth.uid() = user_id) with check (auth.uid() = user_id);
create policy "own decks: delete" on public.decks
  for delete using (auth.uid() = user_id);
```

This is what makes inviting friends safe: every query is implicitly scoped to the
caller's `auth.uid()`. There is no code path that returns another user's decks.

### Preferences stay local — not synced
Theme, view mode, tile size, sidebar state, sort preference, etc. (the 10
non-deck localStorage keys in `SCHEMA.md`) remain **device-local**. They're
device-appropriate — a phone wants a different tile size than a desktop — and
syncing them is both more work and worse UX. No `user_preferences` table in this
version. (`mtg-last-backup` also stays local.)

## Architecture

### `AuthProvider` (new) — `src/hooks/useAuth.tsx`
Wraps the app in `layout.tsx`, *outside* `DeckProvider` (DeckProvider needs to
read auth state). Holds `{ user, session, status, signInWithGoogle, signOut }`.
Subscribes to `supabase.auth.onAuthStateChange`. `status` is
`loading | signedIn | signedOut` so the UI can avoid flicker before the session
resolves.

### Supabase client — `src/lib/supabase.ts` (new)
Single browser client from `@supabase/ssr`'s `createBrowserClient`, reading
`NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY`. Exposes the typed
client. (If we later need server-side session reads we add a server client; not
required for client-only OAuth + RLS.)

### Storage adapter behind `DeckProvider` — `src/lib/deckStore.ts` (new)
A small interface so `DeckProvider` doesn't branch on auth inline:

```ts
interface DeckStore {
  loadAll(): Promise<Deck[]>;
  upsert(deck: Deck): Promise<void>;     // debounced caller
  remove(deckId: string): Promise<void>;
}
```

- `LocalDeckStore` — current behavior, reads/writes `mtg_builder_decks`. Used
  when signed out.
- `SupabaseDeckStore` — maps `Deck` ⇄ row (cards/sideboard/commander_ids as
  JSONB), stamps `updated_at`. Used when signed in.

`DeckProvider` selects the store from `useAuth().status` and otherwise keeps its
existing state shape and mutation API untouched. **Surface components don't
change** — they still call the same `useDeckManager()` methods. This honors
"keep the engine, rebuild the surface": sync is an engine-layer concern hidden
behind the existing provider boundary.

### OAuth callback route — `src/app/auth/callback/route.ts` (new)
Supabase's Google redirect lands here; exchanges the code for a session and
redirects home. Standard `@supabase/ssr` pattern.

## Sync & merge strategy

### First sign-in merge (Phase 3)
On the transition signed-out → signedIn, if local `mtg_builder_decks` is
non-empty:
1. Load cloud decks.
2. For each local deck: if its `id` doesn't exist in the cloud, insert it (it's a
   pre-account deck the user built locally). If the `id` *does* exist (e.g. they
   signed in before on another device, then built more here while signed out — an
   edge case), keep the newer by `updated_at`.
3. After merge, the cloud is the source of truth for the session; local
   `mtg_builder_decks` is left in place as a passive cache/fallback but no longer
   the primary.

Do **not** delete local decks on merge — leave them as a safety net. A later
cleanup can prune, but losing decks is the one unacceptable failure here.

### Steady-state sync
- **On load (signed in):** `loadAll()` from cloud → hydrate provider state.
- **On mutation:** debounced `upsert(deck)` (reuse the existing change-watcher
  timing in `DeckProvider`; ~500ms–1s debounce). Per-deck writes, not whole-
  library writes.
- **Conflict:** last-write-wins per *deck* by `updated_at`. If on load a deck's
  remote `updated_at` is newer than a value we last pushed from this device,
  the remote wins and we show one toast: *"Loaded the latest version of [deck]
  from another device."* No merge UI, no diff — appropriate for one user across
  two devices not editing simultaneously.

This is deliberately simple. **No realtime, no CRDT, no live multi-device
cursors.** That complexity is unjustified for this user base and can be added
later without changing the table.

## Sign-in / out UI

- **Entry point:** a row in `SettingsView` — "Account". Signed out → a single
  "Sign in with Google" button + one line of copy ("Sync your decks across
  devices. Optional — Project Brew works fine without an account."). Signed in →
  show the Google email + "Sign out".
- **Optional** signed-in indicator in the sidebar footer (small avatar/initial)
  — defer to Phase 4 unless trivial.
- **Sign-out** returns to local mode; local decks remain. Confirm before
  signing out only if there are unsynced local changes (Phase 4 polish).

No changes to the home/empty-state framing — accounts must not look required.

## Setup / config (one-time, mostly outside the repo — for Phi)

1. **Supabase project** — create it; copy the project URL + anon key.
2. **Google Cloud Console** — OAuth consent screen + OAuth client (Web). Add the
   Supabase callback URL (`https://<project>.supabase.co/auth/v1/callback`) as an
   authorized redirect URI. **Keep the consent screen in "Testing" mode and add
   the testers' Google emails as test users** — no Google app-verification needed
   for a handful of testers, which fits exactly. (Verification is only required
   to go broadly public later.)
3. **Supabase dashboard** — enable the Google provider, paste the Google client
   id/secret, set the Site URL + redirect URLs to the Vercel domain (and
   `localhost:3000` for dev).
4. **Env vars** — `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` in
   Vercel and `.env.local`. Both are public-safe (RLS does the enforcing).
5. **Run the SQL** — `decks` table + RLS policies (above).
6. **Remote-env network policy** — for Claude Code to run/test the synced app in
   *this* environment, the environment's outbound network policy must permit the
   Supabase domain. Worth confirming before Phase 2 testing.

## Edge cases

- **Signed in, offline / Supabase unreachable:** reads fall back to the local
  cache; writes queue or fail soft with a toast ("Couldn't sync — changes saved
  locally"). Don't lose edits. Full offline-queue robustness is Phase 4+; Phase 3
  just must not drop data.
- **Same user, two devices, edit both while one is offline:** last-write-wins by
  `updated_at` means the later save wins the whole deck; the earlier device's
  edits to that deck can be lost. Acceptable for this user base; the conflict
  toast at least makes it visible. Document it; don't solve it now.
- **Sign in → build → sign out → sign in again:** decks were pushed to cloud
  while signed in; on re-sign-in they load from cloud. Local decks built *while
  signed out* merge up by the first-login rule (id not in cloud → insert).
- **Brand-new account, empty local:** empty cloud library, no merge, no error.
- **Token/session expiry mid-session:** `onAuthStateChange` flips to signedOut;
  provider switches back to `LocalDeckStore`; user can re-auth. No crash.
- **Tester signs in on a shared/family device:** sign-out fully returns to local
  mode and the next person's local decks are untouched (separate from any synced
  account). RLS keeps cloud libraries separate regardless.

## Out of scope (this version)

- Deck sharing, public deck URLs, collaboration, any social surface.
- Email/password, magic-link, or non-Google providers.
- Realtime sync, CRDT merge, live multi-device presence.
- Syncing preferences (theme/view/tile size) to the cloud.
- Normalized per-card tables / cross-deck collection queries.
- A `user_preferences` or `collection` table.
- Server-side rendering of decks / auth-gated routes (app stays client-rendered).
- Account deletion UI / data export beyond the existing local backup feature.

## As-built deltas (v2.0.0)

Where the implementation simplified or diverged from the contract above:

1. **No OAuth callback route.** Used `@supabase/supabase-js` (browser client,
   `detectSessionInUrl: true`) instead of `@supabase/ssr` + a
   `src/app/auth/callback/route.ts`. The app is fully client-rendered, so the
   session is picked up straight from the redirect URL — `redirectTo` is just
   `window.location.origin`. One fewer moving part; the callback route was
   dropped entirely.

2. **Cross-device conflict toast → sync-status indicator.** Rather than a
   per-deck "loaded newer version" toast (which needs per-deck last-sync
   timestamp bookkeeping and threading a toast into the provider), the Account
   section shows a `syncState` (`syncing` / `synced · <time>` / error) line.
   Last-write-wins by `updated_at` still holds; the explicit conflict toast is
   deferred to Phase 4 polish.

3. **Nullable `sideboard` / `commander_ids` columns.** Made nullable (not
   `default '[]'`) so the meaningful "no sideboard enabled" / "no commander"
   state (vs. an empty array) round-trips. Reflected in `supabase/schema.sql`.

4. **Once-per-user merge guard.** Added `mtg-merged-<userId>` localStorage flag
   so the first-login merge runs exactly once per user per device — prevents a
   deck deleted on another device from resurrecting on the next sign-in here.

5. **Always-warm local cache.** When signed in, `DeckProvider` still mirrors the
   whole deck array to localStorage (in addition to cloud pushes), so the local
   copy stays current as an offline fallback — data is never lost if a cloud
   push fails.

6. **Dependency.** Only `@supabase/supabase-js` was added (no `@supabase/ssr`).
